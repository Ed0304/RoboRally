  environment.

  The existing project has been built incrementally. We want to preserve working
  features and avoid unnecessary rewrites.

  Known architecture and implementation details to verify against the
  repository:

  - Frontend: Next.js, React, TypeScript, Tailwind CSS.
  - 3D gameplay: Three.js, React Three Fiber and Drei.
  - Backend: FastAPI.
  - Database: MongoDB Atlas.
  - Database: `roborally`.
  - Collections: `users` and `levels`.
  - Levels are dynamically fetched from the backend; MongoDB is intended to
  remain the source of truth for level data.
  - The frontend uses maze layouts and game logic to handle player movement,
  enemies, lasers, doors, triggers and exits.
  - Enemy patrol routes, line of sight, detection, robot movement, door
  unlocking, restart behaviour and 3D enemy animations have been implemented or
  worked on.
  - The frontend and backend may have existing API contracts, environment
  variables, authentication or other integration details. Inspect them instead
  of inventing replacements.

  The core gameplay must remain deterministic where appropriate. AI-generated
  actions must never bypass game rules or directly manipulate arbitrary game
  state.

  1. Executive summary

  What the repo actually is. A working 3D factory-maze game with keyboard
  controls, plus auth and DB-backed levels — but no AI agent exists yet. The
  agentic loop (mission → plan → validate → execute → replan) is described in UI
  copy and the README vision, not implemented. The game engine (movement,
  collision, lasers, doors, triggers, enemy patrol/detection, win/lose) lives
  entirely in the frontend (src/lib/ + MazeScene). The backend is auth + one
  level endpoint; backend/ai_engine/ is an empty directory.

  Corrections to the brief's assumptions.

  • "MongoDB is source of truth for level data" — only half true. Confirmed: the
    game page fetches levels from GET /api/levels/{id}. But the seed data lives
    in frontend frontend/my-app/data/levels.ts, and a frontend script writes it
    directly to Mongo, bypassing the backend. Two writers, no backend write
    path.
  • "Collect all items" / "Defeat all enemies" goals exist as level metadata,
    but the win check only tests reaching the exit. No pickup or defeat logic
    exists.
  • No Meta integration code exists anywhere. The only traces are a META_API_KEY
    name in backend/.env and UI copy describing a future agent.

  Verified Meta facts that shape the design (all from official docs this
  session): one OpenAI-compatible API at https://api.meta.ai/v1 with a
  MODEL_API_KEY; constrained structured output via JSON Schema; muse-spark-1.3
  for planning; muse-wonder-1.0 as the frontier reasoning model; voice via
  POST /v1/asr/transcribe; images via /v1/images/generations (muse-image-1.0);
  SAM 3.1 (sam-3.1) via Responses API returning boxes+masks; Glimmer 30B runs
  locally (GGUF ~17 GB, <24 GB VRAM); Spark Open is 816B MoE needing 4–8
  datacenter GPUs — local inference is impossible; Muse Code is a terminal
  coding agent (dev-time tool, not an in-product SDK).

  Bottom-line recommendation. Keep the frontend game engine as the authoritative
  executor, add a thin backend ai_engine (planner + validators + model clients)
  behind 3–4 new endpoints, and drive it from a new mission panel mounted on the
  existing game page. Implementation order: stabilize → Spark planning MVP →
  voice → images → SAM perception → Wonder critic → Glimmer → Spark Open last
  with a hosted fallback.

  4. Recommended target architecture

  Principle: extend, don't replace. The frontend stays the game engine and
  action executor (it already is, and it's tested-by-play). The backend gains a
  real ai_engine/ that proposes plans through Meta models and pre-validates them
  against server-side rule mirrors before the frontend executes step-by-step
  through the existing moveRobot/checkGameStatus path. No microservices: one
  FastAPI app, one optional local sidecar (Glimmer inference server).

  meta_client.py (single OpenAI-SDK client, base_url=https://api.meta.ai/v1, key

  Muse Spark 1.3 — core mission planner

  • Purpose: turns natural-language missions + level/observation JSON into a
    structured action plan.
  • Input/output: in: {mission, level layout, robot, enemies, door_open}; out:
    {actions: [{op: move, direction}], reasoning} conforming to our JSON Schema.
  • Location: new backend/ai_engine/{meta_client,action_schema,rules,planner}.py
    + routers/agent.py; frontend src/lib/agent.ts, MissionPanel.tsx.
  • Deps/access (verified): pip install openai;
    `OpenAI(base_url="https://api.meta.ai/v1", api_key=[REDACTED]
  • Effort: M — client is trivial; the work is prompt design, the rules mirror,
    and rejection-reason plumbing.
  • Risks/fallbacks: malformed/unsafe plans → schema + rules mirror reject with
    reasons; outage → disable panel with clear message, keyboard play
    unaffected.
  • Acceptance: real call plans level 1 start→exit; all steps pass rules.py and
    the TS engine; invalid missions get explained rejections.

  Muse Wonder 1.0 — stuck-recovery strategist

  • Purpose: invoked only after N failed/rejected plans; produces a revised
    strategy (e.g. "trigger first, then door"), not the routine move list.
    Distinct from Spark by role and trigger.
  • Input/output: in: mission + failure history + observation; out: strategy
    note + fresh plan in the same schema.
  • Location: same ai_engine, planner.py escalation branch + model field in
    responses; panel shows "escalated to Wonder" state.
  • Deps/access (verified): same API/key/SDK, model="muse-wonder-1.0"; $4/$20
    per Mtok, so gate it behind the failure counter. (Wonder Full is
    Muse-Code-subscription-only — not usable from the API.)
  • Effort: S — reuses the Spark path; new prompt + trigger logic only.
  • Risks/fallbacks: cost/latency → cap escalations per mission (e.g. 2);
    fallback is Spark replan with failure context.
  • Acceptance: a deliberately blocked scenario escalates exactly once and the
    panel shows the strategy note and new plan.

  Muse Image 1.0 — mission art actually shown in game

  • Purpose: generate per-mission briefing art + a factory-wall texture variant
    displayed on the mission briefing header and /start cards. Static assets,
    honestly presented — not realtime inference.
  • Input/output: in: text prompt (+ optional reference image for edits); out:
    PNG saved to public/ai/, referenced by level id.
  • Location: new backend/ai_engine/generate_assets.py seed-time script (run

  • Risks/fallbacks: style drift → fixed style suffix in prompts + human picks

  • Acceptance: each of 6 missions shows its generated art; generation script +

  7. API contracts and data-flow recommendations

  New backend surface (all under /api/agent, JSON unless noted; errors reuse
  FastAPI {"detail": ...} so apiRequest already handles them):

  • POST /api/agent/plan — in:
    {level_id, mission, robot: {x,z,direction}, enemies: [{x,z}], door_open: boo
    l, attempt: int}; out:
    {plan_id, model: "muse-spark-1.3", actions: [{op: "move", direction}...≤24],
     reasoning: string, rejected: [{index, reason}]}. Backend loads the level
    from Mongo itself (never trusts client layout), calls Spark with the JSON
    Schema, then runs every action through rules.py (walls/doors/lasers from
    layout + enemy positions from the request + trigger/door state machine).
    Rejected steps return with reasons; the frontend only executes the approved
    prefix.
  • POST /api/agent/replan — same shape + {failure: {step_index, observed}};
    increments server-side attempt counter; after 2 failures escalates model to
    Wonder (response flags escalated: true). Hard cap: 3 attempts per mission,
    then "mission failed — adapt manually".
  • POST /api/agent/transcribe — multipart audio (≤5 MB, webm/mp3/wav) →
    {text, language?}; relay to /v1/asr/transcribe with PUSH_TO_TALK + game
    keywords. Never returns audio.
  • POST /api/agent/segment — in: {image_b64 ≤2 MB, prompts: string[] ≤4} →
    {detections: [{label, box: [x,y,w,h] normalized, score}], overlay_b64?}; one
    SAM call per prompt, server-side fan-out with timeout.
  • GET /api/agent/health — {meta_api: ok|down, glimmer: ok|down, models: {...}}
    for the panel's status dots and demo-day triage. No secrets in output.

  Data-flow rules: the browser sends observations, never authority — level
  geometry always re-read from Mongo; every model output is validated (schema at
  decode + rules after); the frontend executes via the existing
  moveRobot/checkGameStatus functions, posting each result back so replan sees
  ground truth. Mirror Action/Plan types in src/lib/agent.ts and Pydantic, and
  add shared golden-vector tests later (same input JSON → same verdict on both
  sides).

  8. Security, reliability, performance considerations

  • Secrets: MODEL_API_KEY lives only in backend env / deployment secret store;
    never NEXT_PUBLIC_, never committed (gitignore already covers .env), never
    logged (log model IDs + usage counts only). Migrate META_API_KEY →
    MODEL_API_KEY to match official docs. Move the seed script's MONGODB_URI out
    of frontend/my-app/.env into backend-side tooling or a documented dev-only
    path, and rotate the Atlas credential if it was ever shared.
  • Authn/z: put /api/agent/* behind the existing get_current_user dependency
    (one-line Depends) so demo-day strangers can't spend your Model API budget;
    keep /api/levels public as today. Add the deployed frontend origin to
    origins in main.py at deploy time.
  • Reliability: per-call timeouts (plan 30 s, transcribe 30 s, segment 60 s),
    one retry on 429/5xx with backoff, per-user per-minute caps on agent
    endpoints, hard attempt caps (§7). Every AI failure degrades to fully
    playable keyboard mode with a human-readable reason — the game must never
    depend on a model to function.
  • Cost guardrails: default Spark standard tier; contributor tier only with
    explicit team consent (data trains Meta's products); Wonder gated by the
    failure counter; log token usage per plan for the demo budget sheet.
  • Performance: plans are short (≤24 moves) and levels are tiny — validation is
    microseconds; the latency is model calls, so the panel needs pending states,
    not optimization. Cap upload sizes (§7) to protect the event loop; run
    blocking SDK calls in threads (asyncio.to_thread) or use the async OpenAI
    client.
  • Privacy/evidence: store transcripts of spoken missions only if the user opts
    into history; the usage-evidence log (§9) records model IDs, timestamps, and
    token counts — never mission text or audio — unless consented.

  9. Acceptance tests and demo plan

  handful of backend tests, and CI-less tsc --noEmit + next lint gates.
  Acceptance per area:

  • Planning success: real Spark call on level 1 produces an executable
    start→exit plan; approved prefix reaches exit in the real MazeScene driver.
  • Malformed/unavailable model: kill the key (bad value) → panel shows "planner
    unavailable", keyboard play works; force a schema violation in a unit test →
    rejected[] with reasons, nothing executes.
  • Invalid/blocked moves: mission "walk through the north wall" → steps
    rejected with "wall at (x,z)"; robot never leaves valid tiles (assert via
    canMoveTo oracle).
  • Door/trigger: level 3 mission → plan must route via ! before D; stepping on
    trigger opens door (existing toast fires); pre-trigger door steps rejected.
  • Enemy/laser: plotted path through a patrolling enemy's tile or laser tile is
    rejected or flagged; walking into detection still kills via checkGameStatus
    (no AI bypass).
  • Bounded replan: scripted blockage triggers replan with new observation, max
    3 attempts, then clean failure state; Wonder escalation fires exactly once
    when configured.
  • Creds/timeouts/rate limits: missing key, 30 s timeout, simulated 429 →
    user-facing messages + /health reflects down; no stack traces in UI.
  • Voice errors: empty file, oversize file, mic denied → typed-input fallback
    messaging; gibberish audio returns text the user can edit before planning.
  • Segmentation: level 5 scan finds enemies (box overlap vs ground truth);
    empty frame yields zero detections; oversize image rejected client-side.
  • Open weights: Glimmer debrief generates with api.meta.ai blocked (hosts-file
    or proxy test); sidecar down → static fallback line.
  • Regression: tsc --noEmit clean, next build passes, levels 1–6
    keyboard-completable, auth flows unchanged, check-mazes (fixed) reports all
    solvable.
